# AI Infra Doctor

**面向 AI 工作负载的轻量级智能监控与故障诊断工具**

AI Infra Doctor 是一个面向 AI 基础设施运维场景的开源原型项目，尝试将主机资源监控、异常检测、多指标关联分析和故障诊断整合到一个轻量级 Web 系统中，帮助开发者更直观地了解系统运行状态，并初步定位潜在的资源瓶颈。

项目采用模块化设计，当前重点实现系统资源监控、规则检测、多指标关联分析、规则诊断与可视化 Dashboard，为后续接入真实 AI 推理工作负载、GPU 监控及大模型辅助诊断提供基础。

## 1. 项目背景

随着 AI 模型训练与推理任务不断增加，CPU、内存、磁盘、网络以及 GPU 等资源的使用情况会影响任务运行效率。当服务出现延迟升高、任务排队或资源利用率异常时，仅观察单一指标往往难以判断问题原因。

本项目希望通过统一的监控界面展示关键资源状态，并结合阈值检测和多指标关联规则，对潜在异常进行初步识别和解释，降低排查问题的理解成本。

当前项目定位为可运行、可演示、可扩展的原型系统，不将模拟工作负载数据描述为真实生产环境数据，也不宣称已经具备完整的生产级故障诊断能力。

## 2. 核心功能

### 2.1 主机资源监控

使用 Python `psutil` 采集当前运行主机的基础资源指标，包括：

- CPU 使用率
- 内存使用率
- 磁盘使用率
- 网络发送与接收速率

采集结果通过后端 API 提供给前端 Dashboard 展示。

### 2.2 异常检测

基于配置的阈值规则识别部分资源异常，例如 CPU、内存或磁盘使用率超过设定阈值时生成相应的异常信息。

当前异常检测以规则为主，后续可以扩展统计方法、时间序列分析和机器学习模型。

### 2.3 多指标关联分析

单个指标异常不一定能够直接解释问题。本项目通过关联规则尝试结合多个指标判断潜在瓶颈。

例如，在模拟工作负载中，当 CPU 使用率较高、GPU 利用率较低，同时请求延迟和任务队列长度达到设定条件时，系统可以识别出潜在的 CPU 瓶颈，并生成对应的关联分析结果。

该结果属于规则推断，不代表已经通过真实 GPU 集群或实际推理服务验证。

### 2.4 规则诊断

系统根据检测结果和关联分析结果生成可解释的诊断信息，帮助用户了解可能存在的问题及其判断依据。

当前可演示的诊断结果主要来自规则诊断与多指标关联分析，而非已经集成的大模型自动诊断流程。

### 2.5 Web Dashboard

项目提供轻量级 Web 可视化界面，主要展示：

- 主机资源使用情况
- 资源指标变化曲线
- AI 工作负载相关指标
- 异常检测结果
- 多指标关联分析结果
- 故障诊断信息

前端使用 HTML、CSS、JavaScript 和本地 ECharts 资源实现，支持定时刷新。当前方案无需单独启动 Node.js 前端开发服务器。

## 4. 系统架构

```text
                 ┌──────────────────────┐
                 │    主机资源采集       │
                 │ CPU / Memory / Disk  │
                 │ Network              │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │     异常检测模块      │
                 │     Threshold Rules  │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │    多指标关联分析     │
                 │  Correlation Rules   │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │      规则诊断模块     │
                 │  Explainable Results │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │     FastAPI 后端     │
                 │      REST API        │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │    Web Dashboard    │
                 │  Metrics / Findings │
                 └──────────────────────┘
```

此外，项目包含独立的 LLM 诊断客户端模块，作为后续扩展能力。

## 5. 数据来源与功能边界

为避免混淆，项目当前的数据来源与功能状态说明如下。

| 内容 | 当前实现 |
|---|---|
| CPU、内存、磁盘监控 | 通过 psutil 采集真实主机指标 |
| 网络速率 | 根据主机网络计数器计算 |
| AI 工作负载指标 | 使用模拟数据 |
| 异常检测 | 基于规则与阈值 |
| 多指标关联分析 | 基于预设关联规则 |
| 故障诊断 | 基于规则生成可解释结果 |
| Dashboard | 已实现 Web 展示与定时刷新 |
| LLM 诊断客户端 | 已有独立模块；尚未接入 Dashboard 和统一状态 API，端到端真实模型调用尚未验证 |
| 真实 GPU / 推理服务集成 | 当前版本尚未完成 |

项目中的模拟工作负载指标用于验证数据展示与关联分析流程，不代表真实推理服务的运行数据。

## 6. 运行方式

### 6.1 环境要求

- Python 3.13（当前项目使用的 Python 环境）
- pip

### 6.2 克隆项目

```bash
git clone https://github.com/m11tt/AI-Infra-Doctor.git
cd AI-Infra-Doctor
```

### 6.3 创建虚拟环境

Windows PowerShell：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

如果 PowerShell 无法激活虚拟环境，也可以直接使用虚拟环境中的 Python 执行后续命令。

### 6.4 安装依赖

```powershell
python -m pip install -r requirements.txt
```

### 6.5 启动服务

在项目根目录执行：

```powershell
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

启动成功后，在浏览器访问：

- Dashboard：<http://127.0.0.1:8000/dashboard>
- 首页：<http://127.0.0.1:8000/>
- 状态 API：<http://127.0.0.1:8000/api/v1/status>
- API 文档：<http://127.0.0.1:8000/docs>

> 以上为**本机地址**（`127.0.0.1` 是本机回环地址），需要先在本地启动服务才能访问，在别人的机器或线上直接点击无法打开，属正常现象。

如果使用虚拟环境，请确保启动命令调用的是该环境中的 Python。

## 7. 测试

项目使用 pytest 进行自动化测试。

安装开发依赖：

```powershell
python -m pip install -r requirements-dev.txt
```

运行测试：

```powershell
python -m pytest tests/ -q
```

测试主要用于验证项目模块、规则逻辑及相关接口行为。测试通过不等于已经验证真实 GPU 集群、生产级推理服务或大模型诊断效果。

提交前请以实际运行结果更新测试状态。

## 8. 项目特点

### 轻量化架构

采用 Python、FastAPI 和静态前端构建，减少额外的前端构建与部署环节，便于本地运行和演示。

### 多指标联合判断

不局限于单个资源阈值，而是尝试结合 CPU、GPU、延迟和队列等指标，通过规则分析潜在的资源瓶颈。

### 可解释的诊断结果

通过明确的检测条件与关联规则生成诊断结果，便于理解系统为何产生相应判断。

### 模块化与可扩展性

将监控、检测、关联分析、诊断和接口服务拆分为相对独立的模块，为后续扩展真实工作负载采集、GPU 监控、历史数据分析和大模型辅助诊断保留空间。
